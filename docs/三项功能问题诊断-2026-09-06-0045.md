## 问题 1：窗口最大化记忆失效

**根因：启动时序冲突——「先恢复最大化，后启动同步尺寸」，后者无条件退最大化。**

1. Rust setup 建窗后立即恢复：`restore_window_state`（src-tauri/src/lib.rs:726 → :435-443）读 `$DSH_HOME/dsh-hub-window-state.json` 的 `maximized:true` → `win.maximize()` ✅
2. 数秒后 sidecar 内 dsh-hub 插件 apply，连接壳时**无条件**套用配置尺寸：src/index.ts:252-255 `h.applySize(effective.width, effective.height)`（该行为 887667c 引入，属长期存在而非 rc.1 回归）
3. Rust 侧 `set_window_size` 统一 unmaximize-first（src-tauri/src/managers/window_ops.rs:73-78，R2-3 修复时确立的"双路径行为一致"决策）：`is_maximized → unmaximize → set_size`
4. 结果：每次启动最大化都被打回窗口化，且 resize 监听（lib.rs:761-772）随即把 `maximized:false` 写回状态文件

**修复方案（推荐）**：`set_window_size` 增加可选 `unmaximize` 参数（默认 true 保持 A7 行为），boot 同步路径传 `unmaximize:false`——窗口处于最大化时直接跳过（最大化状态优先于配置尺寸）。备选：boot 路径干脆不调 applySize（Rust 建窗已有尺寸优先级链 window.rs:112-135），但需确认"配置分辨率"设置项的启动同步语义是否要保留。

## 问题 2：模型列表未跟随自定义嵌套菜单

**根因：hub client 入口刻意不注入 `modelDirectories`，apply 时软探测可能落空 → installModelSelect 静默 return → 官方 seat 保留。**

- hub client `inject = ['slots','workspaces','sessions']`（src/client/index.ts:92），注释明言 modelDirectories 刻意不注入（:88-91，怕 PENDING 整个插件）
- `installModelSelect` 对 `slots/modelDirectories/sessions` 逐个 `ctx.get`，任一 undefined 即**无日志静默返回**（src/client/model-select.tsx:388-391）→ 无法察觉
- dsh 0.1.2-rc.1 侧机制**未变**（子代理逐项比对 tag dsh-v0.1.2-rc.1）：`conversation.input.model` slot 声明（ui-conversation slots.ts:147）、InputBar 渲染点（InputBar.tsx:467）、SlotCore 优先级语义（升序、最低者渲染，ui-slots index.ts:534-539）、官方注册（无 priority=0，ui-model-selection index.ts:158-178）与 rc.2 完全一致；官方 slot-catalog 甚至标注该 seat 可被第三方 shadow（slot-catalog.ts:826-831）。hub 的 priority -1 写法正确
- rc.1 变化的是服务布局：`slots` 服务移至 ui-renderer 包、模型目录数据源换为共享 `session/modelCatalog` + projection——`modelDirectories` 的提供时机（ui-model-selection roster 末段）与 hub apply 的先后无顺序保证 → 软探测落空概率大增
- 次要嫌疑（已排除/降级）：`sessions.subagentAddress` rc.1 仍存在（ui-commands client.js:526 实证）；组件空态防御完备（loading/groups:[]/current:null 均有分支），渲染崩溃 abdicate 可能性低

**修复方案（推荐）**：`inject` 数组加入 `'modelDirectories'`（web profile 必有 ui-model-selection，不会 PENDING；headless profile hub 本就不装配）+ installModelSelect 守卫改为 warn 日志不再静默。修复后隔离冒烟验证嵌套 seat 渲染。若保守，可保留软探测但加"延迟等待服务出现"机制（复杂度高，不推荐）。

## 问题 3：自定义模型无法切换思考强度

**根因：effort 档位不是 UI 自造，而是 Host catalog 的模型元数据；自定义模型条目没有 reasoning 元数据 → 只有「默认」。**

- 档位链：Host `buildModelCatalog` → `ctx.llm.resolveModelInfo(provider, model)` → 适配器 `reasoning.efforts`/`defaultEffort`（session-controller catalog.ts:24-37）→ 官方 UI（ModelSelect.tsx:89-100）与 hub UI（model-select.tsx:195-201, :276）都只按该元数据显示档位
- pi-ai 适配器（自定义 provider 走它）：手工声明的模型条目 `reasoning: base?.reasoning ?? false`（llm-pi-ai catalog.ts:662-675）——不声明就没有 efforts
- **Host 请求路径会校验** effort ∈ 声明的 efforts（llm/src/index.ts:853-872、adapter.ts:157-168 `UNSUPPORTED_REASONING_EFFORT`）→ **hub UI 不能硬造档位**，造了也会被拒
- 关联：因问题 2，用户当前看到的其实是**官方**选择器——官方对无元数据模型同样只显示默认（ModelSelect.tsx:255-261），两 UI 行为一致

**修复方案**：
- **路径 A（配置面，立即可用）**：在 dsh 设置的自定义模型条目声明 `reasoningEfforts`（pi-ai config schema 支持，config.ts:302；catalog.ts:688-716 翻译为 thinkingLevelMap）→ 档位即出现在官方/hub UI。可先出文档指引。
- **路径 B（hub 功能增强，可选立项）**：hub 设置卡增加"自定义模型思考强度"配置项，经官方 settings/配置面写入模型条目 `reasoningEfforts`——需单独设计（写入权限/格式/与 dsh 设置 UI 的同步）。
- 前置依赖：问题 2 修复后 hub 嵌套菜单才可见。
