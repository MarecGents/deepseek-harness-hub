# 关键踩坑记录（勿重蹈）

> 本项目开发过程中踩过的坑，按“现象 → 原因 → 正确做法”整理。新坑持续补充。

## 配置与 dsh 集成

1. **settings 命名空间白名单**
   - dsh api-proxy 的 `settings.describe` 只返回硬编码 `WEB_SETTINGS_NAMESPACES` + model providers + product 名单。
   - 第三方插件命名空间 RPC 永远看不到（官方注释 "deferred work"）。
   - 正确做法：第三方配置 UI 一律走插件自有 HTTP 路由。

2. **route 唯一性**
   - `ctx.webServer.register` 的 exact route 同 path 不能注册两次。
   - 正确做法：GET/POST 合并进一个 handler，按 method 分发。

3. **client 插件机制**
   - patch 行 name 用包名。
   - client row 由 modules node half 扫描 `dsh.client` 自动编入 `__DSH_BOOT__`，无需特殊 client 行。

4. **client 使用 `ctx.workspaces` 必须注入 `workspaces`**
   - `inject` 只写 `slots` 时 `ctx.workspaces` 为 undefined，托盘“新建任务”会静默失败。
   - 正确做法：`inject: ['slots', ..., 'workspaces', 'sessions']`。

5. **事件类型合并**
   - `session/event` / `agent/created` 等 Events 由 `@deepseek-ai/dsh-session` / `@deepseek-ai/dsh-agent` 声明合并。
   - 使用方需显式 `import type {} from` 这两个包。

6. **顶层会话 delegationDepth 是 undefined**
   - dsh 顶层会话 `delegationDepth` 为 absent（undefined），不是 0。
   - 判断顶层会话时不要写 `!== 0`，应写 `(session.header?.delegationDepth ?? 0) !== 0`。

## 窗口与 WebView2

7. **窗口退化 bug**
   - 状态记忆必须校验最小尺寸/坐标，防 boot 期 0 尺寸持久化。
   - `??` 不会跳过 0，要显式判断。

8. **webviewjs 无关闭拦截**
   - `window-close-requested` 只是通知，没有 preventDefault。
   - 关闭到托盘用“不 exit + 隐藏保活窗口重建”方案。

9. **最小化到托盘恢复闪烁**
   - hide 前先 `setMinimized(false)` 清标志，showWindow 前同样清理。

10. **splash 期间主题探测**
    - splash 页无主题标记，探测必须三态（`na` / `-1`），否则标题栏启动时闪浅色。

11. **主动退出必须写 quit.marker + `process.exit(0)`**
    - webviewjs 的 `app.exit()` 在 Windows 可能以 `0xC0000005` 崩溃。
    - launcher 会把非 0 退出误判为异常并自动重启；主动退出走 `quit.marker`。

## 主题与系统调用

12. **PowerShell 慢**
    - 冷启动约 1.3s/次，常驻 stdin pipeline 每行约 1s。
    - 标题栏 Dwm 调用必须用 FFI（koffi，~1ms），PowerShell 仅兜底。

13. **`explorer.exe` 不要加 `windowsHide: true`**
    - 会导致 Explorer 窗口隐藏启动，“打开工作区”看起来无反应。
    - 需要前置时用后台 PowerShell 按窗口标题查找并 `AppActivate` + 短暂 TOPMOST。

14. **evaluateScriptWithCallback 返回值带引号**
    - 字符串结果被带引号序列化（`'dark'` → `"dark"`），`.trim()` 无法匹配。
    - 探测一律用数字（1/0/-1）避免歧义。

15. **托盘桥返回值用数字**
    - 字符串返回值同样带引号，host 判断永远失败并重复派发。
    - `dispatchScript` 成功/未就绪返回 `1/0`。

## 右侧栏 / 前端

16. **shell.overlay 方案不可用**
    - 官方 overlay 层在 AppFrame 内部，fixed 子元素定位/裁剪行为异常，侧边栏会跑到左侧。
    - 正确做法：参考 DSH-better-sidebar，用 **body portal** 挂载右侧栏。

17. **新对话无法展开**
    - 官方 details 列对 blank session 强制 width 0（`detailsSession` 仅在 `blank === false` 时传入）。
    - 不要依赖 details slot 承载主侧边栏；用 body portal 自管宽度。

18. **body portal 需要 react-dom**
    - tsdown 配置已 externalize `react-dom/client`，但构建需要本地安装 `react-dom` 与 `@types/react-dom`。
    - 运行时由 dsh 平台模块表提供。

19. **npm install 会清掉 SDK junction**
    - `build-client` 建立的 `@deepseek-ai/dsh-*` junction 会被 `npm install` 移除。
    - 装完依赖后必须重新运行 `npm run build:client`。

20. **postinstall 可能改动 bin/launcher.vbs**
    - `npm install` 后 `git status` 常出现 `bin/launcher.vbs` 被修改。
    - 提交前确认是否为无关改动；不需要时 `git checkout -- bin/launcher.vbs`。

## 构建 / 发布 / 合并

21. **合并 PR 时生成文件冲突**
    - `lib/client.js.map`、`package-lock.json` 等生成文件极易冲突。
    - 正确做法：保留源码合并结果后，重新 `npm install` + `npm run build` + `npm run build:client` 再提交。

22. **默认 npm registry 可能是华为云镜像**
    - `npm view` / `npm install` 默认走 `https://repo.huaweicloud.com/repository/npm/`，新版本可能未同步。
    - 发布和验证请显式使用 `--registry=https://registry.npmjs.org/`。

23. **发布候选版用 `--tag rc`**
    - 直接 `npm publish` 会覆盖/影响 `latest`。
    - 候选版应 `npm publish --tag rc`，用户安装用 `npm install @marecgents/dsh-hub@rc`。

## 多实例 / 会话数据

24. **多个 dsh 实例并存会损坏会话数据（已实际发生）**
    - 现象：同一会话在两个 dsh 实例（不同端口）中同时打开 → 该会话读取报 corrupt、GUI 不可用。
    - 根因：两个实例共享同一 `$DSH_HOME/sessions` 存储；在同一个 turn 处交错 append 时产生两组相同 seq 的冲突事件（一组「interrupted 死分支」+ 一组「真实活分支」），`SessionLogScanner` 检测到 seq 回退 → 判定会话损坏。
    - 修复（2026-08-16）：帧级字节拼接剔除死分支 4 行（checksum 无需重算），保留活分支后续 2 万+ 事件；备份 `.corrupt.bak` 可回滚。详见 `docs/会话损坏修复记录-2026-08-16-1023.md`。
    - 预防：
      - dsh-hub 启动时检测已有 dsh 实例（任意端口），默认**拒绝**共存（设置 → DSH HUB 设置 → 「允许同时运行多个实例」未勾选时直接拦截）。
      - 确需共存须勾选该选项，并确认严重警告（共享 `$DSH_HOME`、同会话双写会损坏日志）。
      - 任何情况下都不要在两个实例中同时操作同一个会话。

## 设置保存 / 皮肤

25. **设置保存回环不可信任服务端响应（勾选"保存后又被取消"）**
    - 现象：设置卡片勾选 → 保存 → 勾选被取消（或重开卡片发现没保存）。
    - 根因（两类）：
      - a) 运行中的 dsh 实例内存里是**旧代码**（Node 启动时加载 lib/，之后改的 src/lib 不生效）——旧 host 的 POST 白名单没有新字段 → 响应缺字段 → 客户端 `setDraft(saved)` 静默回退。本机实测：实例 10:43 启动，早于皮肤/声音/新白名单，重启即恢复。
      - b) 双实例并存时，旧 host 的 `writeShellConfig` 用**旧 DEFAULT 合并回写**，会抹掉新 host 写入的新字段（skin/soundEnabled）→ 皮肤选择/勾选被"取消"。
    - 正确做法：
      - 客户端保存成功路径 `setDraft({ ...saved, ...patch })` **回放提交的 patch**——勾选永不静默回退；`config` 保持服务端真相，真丢字段时显示"未保存"而非消失（dsh-hub 已修复）。
      - 测试新构建前先**重启**实例（会话持久化在 `$DSH_HOME/sessions`，重启不丢）；不要在旧实例上判断新功能行为。
      - 新增配置字段必须三处一致（ShellConfig 接口 / DEFAULT_SHELL_CONFIG / POST 白名单），漏白名单 = 本坑重现。

26. **皮肤只覆盖 alias 背景会导致左右侧边栏不跟随（浅色停留官方白）**
    - 现象：浅色模式下应用皮肤，只有中栏背景变了，左导航/右侧栏还是官方白。
    - 根因：dsh 左导航背景用 `--dsw-specific-sidebar-fill`（specific token），卡片徽章用 `--dsw-alias-bg-module-platform`，浮层用 `--dsw-specific-menu`——都不在皮肤原本只覆盖的 alias bg 集合里。
    - 正确做法：皮肤必须同时覆盖 alias 全量 + specific 组（sidebar-fill / sidebar-nav-item-active-accent / sidebar-nav-item-active / sidebar-nav-item-hover / menu）+ bg-module-platform，且 `skins.ts` 的 `buildCss` 按 `specific` 字段输出 `--dsw-specific-` 前缀（alias 与 specific 放错位置 = 前缀错误 = 覆盖无效）。详见 `docs/skins/AGENTS.md`。

## 进程身份 / 音源

27. **Windows 进程身份 = exe 内嵌资源（不是运行时改名）**
    - 现象：任务管理器把 dsh-hub 显示为 "Node.js JavaScript Runtime" + node 图标。
    - 根因：进程显示名来自 exe 的 VERSIONINFO（ProductName/FileDescription）+ 内嵌图标 + 文件名；dsh 运行时就是 node.exe，资源是微软的。
    - 正确做法（dsh-hub 已实现）：`bin/hub-exe.mjs` 复制当前 node.exe → `dsh-hub.exe` / `dsh-hub-guard.exe`，用 `@electron/rcedit` 替换图标与版本信息（ProductName=DeepSeek Harness Hub / Launcher），缓存 `$DSH_HOME/dsh-hub/bin/` + stamp（node 升级自动重建）；launcher re-exec 为 guard、spawn 应用用 patched exe。**补丁 exe 不可提交进 git**（跨机器/node 版本会失效）；生成失败回退 cmd shim。
    - 教训：别想用运行时 API 改名进程——任务管理器读的是 PE 资源。

28. **提示音素材不要原封复用他人项目的文件**
    - 现象：曾把 DeepSeek-Reasonix 的 4 个 mixkit WAV 复制进 assets/sounds（用户要求改为自有资源）。
    - 正确做法：原创合成（`scripts/synthesize-sounds.mjs`，44.1kHz/16bit WAV，正弦+谐波+指数衰减包络）——零版权、体积 ~30-80KB、播放链路不变（winmm PlaySoundW 只认 WAV）。可脚本化下载的免费库（Pixabay/Mixkit）只提供 MP3，无 API key 拿不到 freesound 的 WAV，故合成是 WAV 原生播放的最优解。

## 前端 DOM 增强（置顶会话）

29. **ui-workspace 的 CSS-module hash 不可作为插件定位锚点**
    - 现象/风险：`ui-workspace` 的行/标题/操作区类名是构建期 hash（`.YDXeBa_*`），dsh 升级重编译即变——把功能定位写死在 hash 上 = 升级即失效（PR #4 原实现即如此）。
    - 正确做法（dsh-hub 已实现）：定位只用 **framework 稳定契约**——`div[data-slot="sidebar.workspaces"]`（slot 渲染器固定输出，web-react/scoped-slots）、`role="tree"`、`div[role="treeitem"]`（排除 `[aria-expanded]` 分组行、`:not(button)` 搜索行）；**行→会话映射用内容匹配**（行内文本 == displayTitle，同名整组跳过，读错=跳过不误标），插入位置 = 匹配到的标题元素之后。
    - 单点豁免（仅 2 处，dsh 升级回归清单必查）：① 自绘 pin 图标（官方 `Icon*Outline16` 无 pin，见根 AGENTS §3 豁免条款，官方提供后切换）；② 无（标题提取已用内容匹配替代，零 hash）。
    - 数据正确性纪律：pins 写路径必须等 `phase==='ready'` 基线落地（空 byId 时收缩会清空 pins.json，真实事故风险）；boot 结果与用户交互增量合并（dirtyDelta），剪枝连续 2 次 ready 快照缺失才删；disposer 必须移除注入 DOM（HMR 重装防僵尸闭包写）。

30. **官方组件内联 token 不被皮肤覆盖（升级检查项，勿用 body.style 竞争）**
    - 现象/风险：部分官方表面**直接硬编码颜色**而不走 `--dsw-*` token——例如 ui-primitives Tooltip 文字固定 `bluish-00` 白、部分按钮变体。皮肤注入的 `<style>` 只对走 token 的表面生效；`body.style.setProperty` 竞争注入顺序/特异性不可控（预留设计，见修复方案 D1）。
    - 真实事故：terminal/aurora 深色曾把 `tooltip-bg`/`toast-bg` 设计为"反色浮层"（`#a9f0a9` / `#e2dcff` 亮底），但官方 tooltip 文字固定白 → 白字浅底不可读；2026-08-16 修复为深底（`#0e1c10` / `#151331`）。
    - 正确做法：皮肤升级回归清单——① 深色模式逐表面检查 tooltip/按钮/气泡文字可读；② 新增官方 token 时补进 5 套皮肤浅/深两套（`docs/skins/AGENTS.md` 覆盖纪律表，含 `bubble`/`bubble-highlight`）；③ 浮层 token 一律"深底浅字"，勿再引入反色浮层。

31. **置顶会话升级冒烟清单（锚点契约漂移）**
    - 现象/风险：置顶功能定位依赖 framework 稳定契约（`data-slot="sidebar.workspaces"`、`role="tree"`、`div[role="treeitem"]:not([aria-expanded])`）+ 内容匹配（行内文本 == displayTitle）+ 几何镜像（`--dsh-session-list-*` var）。dsh 升级若改变列表 DOM 结构/标题元素/搜索行形态/分组与扁平布局切换，置顶会静默失效或误标。
    - 正确做法：每次 dsh 升级后跑置顶冒烟清单——① 分组/扁平模式行 pin 按钮出现、置顶/取消生效；② 搜索有结果/清空/空结果三种状态置顶区不闪现、不注入搜索行；③ 会话折叠/展开后行状态保持；④ 同名会话多开整组跳过（不误标）；⑤ 重启 pins 保留、多标签同步（storage 事件）；⑥ 置顶区与行对齐（edge-inset/scrollbar var 回退值生效）。详见 docs/深度审查报告-2026-08-16-1603.md D 组。

32. **背景图必须注入应用 frame 层，且锚点不可用 CSS-module hash**
    - 现象/风险：PR #6 首版把背景图注入 `body{background-image}`——dsh 的 AppFrame（`.frame{background:var(--dsw-alias-bg-base)}`）以不透明 token 背景全屏覆盖 body，图片**完全不可见**（三轮审查实证：注入红色样张，frame 区域像素无红色）。若再图省事用 frame 的 hash 类名定位（`.pI_x6G_frame`），dsh 升级重编译即失效（同 #29）。
    - 教训 1（渲染层级）：**新增背景/覆盖层必须先验证目标层的绘制顺序**——`body` 背景在 AppFrame 之下；负 z-index 伪元素按 CSS2.1 Appendix E 绘制序（step2）确定性垫在 frame（positioned, step6）之下，同样不可见。
    - 教训 2（结构锚点）：frame 是 `#root` 下唯一带内联 `grid-template-columns` 的元素——**`#root div[style*="grid-template-columns"]` 是唯一稳定非 hash 锚点**（`#root > div` 是 slot 出口 `display:contents` 无盒，不可用；frame 无稳定 data-*）。升级冒烟项：该选择器必须仍唯一命中 frame。
    - 教训 3（第二层覆盖，2026-08-16 真机复现）：**frame 背景命中 ≠ 可见**——frame 的三个栏子元素（sidebarCol 280px + centerCol 内容根 1000×720 白底等）盖满全窗，把 frame 背景图**完全遮死**（用户真机：选图"闪烁一下没变化"；像素实测 frame 注入红色后中栏仍全白）。必须**透明化中栏内容根**才可见：`[data-slot="conversation"] > div`（官方 slot 契约锚点，非 hash）→ `background-color:transparent`。侧栏保持皮肤 fill 不动。升级冒烟项：`[data-slot="conversation"]` 直接子 div 必须仍唯一命中中栏内容根。
    - 正确做法（dsh-hub 已实现）：`backgrounds.ts applyBackground` 注入规则——① `#root div[style*="grid-template-columns"]{background-image:linear-gradient(rgba(0,0,0,.25),...),url(...)!important;...}` 双层背景（蒙层 + 图片都在 frame 自身背景层，零层叠上下文风险；`background-color` 保留 token fallback）；② 左/中/右三栏表面 `color-mix(原 token 75%, transparent)`（背景图透出 ~25%，用户要求 20-30%；左栏 = sidebarCol 设 transparent + `[data-slot="sidebar"] > div` 75% fill，中栏 `[data-slot="conversation"] > div` 75% bg-base，右栏 `[data-slot="details"] > div` 75% bg-base）；③ 自研右侧栏（body portal）把图画在自身上（多层背景 `[fill 75% 渐变] + [黑蒙] + [url]`，内部 `[class*="mg-rs-"]` 透明，见教训 5）。`'none'` 清空注入（全部移除）。静态资源走 `/api/dsh-hub/backgrounds/*`（backgrounds-api.ts，正则白名单防路径穿越，`decodeURIComponent` 包 try/catch 保证畸形 % 编码返回 404 而非 400）。
    - 教训 4（双层叠加，2026-08-16）：给"容器 + 内容根"**同时**设半透明会叠乘——0.75²=0.9375，背景图只剩 ~6%（用户实测左右栏"几乎没变化"）。半透明只能加在**单层**：容器（sidebarCol/detailsCol）要么设 `transparent`（露出下层）要么不设，75% 只给内容根一层。
    - 教训 5（fixed portal 半透明合成，2026-08-16 真机复现）：**body portal 的 fixed 面板，半透明背景（color-mix / opacity / backdrop-filter）都不会透出背后的内容**——WebView2/Chromium 合成器对 fixed 合成层不采样背后（像素实测：右栏无论 color-mix 75% 还是 opacity 0.75 都呈纯 fill 色；backdrop-filter 更直接导致面板内容消失变纯色块）。自研右侧栏（body portal）只能**把背景图画在面板自身上**：`background-image: [fill 75% 渐变层] + [黑蒙 25%] + [url 图]`（多层背景，`background-attachment: fixed` 与 frame 对齐），并把面板内部 `[class*="mg-rs-"]` 背景透明化避免叠层——像素实测 25% 透出与理论值一致（RGB(222,171,186) ≈ 75% fill + 25% 蒙层图）。教训：**body portal 元素只能在"加载插件的真实实例"验证**（CLI 实例无插件、无右侧栏）；任何半透明/毛玻璃方案先像素验证。
    - 教训 6（fixed 合成层是根因，与 DOM 位置无关，2026-08-16 真机复现）：曾评估"把右侧栏注册进官方树（detailsCol/grid 第 3 列）以复用官方流内混合行为"——实验证伪：**在 `#root` 内注入 position:fixed 探针 + color-mix 75%，同样不透出背后**（像素 RGB(232,228,247) 纯 fill）。即 **`position:fixed` 本身触发合成层、半透明背景不采样背后，与元素挂 body 还是 #root 无关**；唯一能透出的是**非定位流内元素**（中栏内容根 static ✓）。而"流内右栏"= 占用官方 detailsCol/grid 第 3 列 = 与官方 details 冲突 + 修改官方内联 grid-template-columns = 侵入官方布局（违反 stable anchors 纪律）。**结论：右栏浮层无法通过"注册进官方树"获得透出能力，自绘画图（教训 5）是唯一可靠路径**；官方树注入方案永久归档为不可行。

33. **全新环境 `npm i -g` 后「连续异常退出」（ERR_MODULE_NOT_FOUND）**
    - 现象（2026-08-16 测试电脑真机）：全新机器装好 Node + `npm i -g @marecgents/dsh-hub` 后，点桌面快捷方式弹「dsh-hub 连续异常退出，请看 dsh.log」；日志显示 `Cannot find package '@marecgents/dsh-hub' imported from C:\Users\...\.dsh\profiles\web\`（ERR_MODULE_NOT_FOUND），崩溃 3 次后放弃。

## dev-v2 Tauri 收口期踩坑（2026-08-19）

38. **插件 fiber 拆除硬杀进程**
    - 现象：host 插件 dispose 时整实例退出（dispose → onExit → exitProcess 链路）。
    - 原因：把「插件 fiber 拆除」误当「应用退出」，拆除时硬杀进程。

    - 现象：dsh 升级后首启即崩（peer 区间过旧）。
    - 原因：peer 声明 ^0.0.1-rc.1 与已发布的 dsh 0.1.0-rc.7 不匹配。
    - 正确做法：peer 对齐 `^0.1.0-rc.6`（与 dsh 实际版本区间一致，已入库）。

    - 现象：GNU 工具链链接 dsh_hub_lib.dll 报导出序号溢出。
    - 原因：mingw ld 自动导出 windows crate 全部符号，序号超 PE/COFF 上限（tauri-apps/tauri#10843）。
    - 正确做法：`src-tauri/.cargo/config.toml` 加 `--exclude-all-symbols`（已入库；桌面 exe 静态链接 rlib，cdylib 无需导出符号）。

41. **cmd-shim 兜底只杀 cmd.exe 留下 node 孙进程孤儿**
    - 现象：退出/重启后 dsh 端口仍被占用，下次启动被多实例门禁锁死。
    - 原因：cmd /c 兜底路径的 child 是 cmd.exe，kill 只杀它，node 孙进程残留。
    - 正确做法：kill 后补 `taskkill /PID <pid> /T /F` 杀整棵进程树 + resolve 硬化（优先解析 shim 为 node.exe + entry 直接 spawn）。

    - 现象：toast 点击无法回到窗口（插件 2.3.3 无 onClick）。

    - 正确做法：改用 notify-rust 直弹 + `wait_for_action` 实现点击回窗。

43. **本机 WQL `-or` 报无效查询 0x80041017**
    - 现象：多实例检测的 CIM 查询报 0x80041017 无效查询。
    - 原因：WQL 顶层 `-or` 连接条件不被接受（运算符优先级歧义）。
    - 正确做法：把 OR 条件括号化（`(A) or (B)`）再查询。

44. **Rust `if let` scrutinee 的 MutexGuard 临时存活导致内层重锁死锁**
    - 现象：supervisor 线程偶发死锁/卡死。
    - 原因：`if let Some(child) = lock().unwrap()` 中 Guard 活到整个块结束，块内再次 lock 同一把锁 = 重入死锁（clippy::if_let_mutex）。
    - 正确做法：先 `take()` 出来再进 if-let 做 `try_wait`，块内不持锁。
