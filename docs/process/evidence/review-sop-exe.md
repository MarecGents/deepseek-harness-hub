## 一、问题清单

### 【Major-1】验收断言脚本被引用但无实现任务，指标"可自动断言"落空
- **描述**：SOP 多处验收/指标引用"脚本"作为断言手段，但全篇任务清单（T1.x–T5.x）中**没有任何任务创建这些脚本**：
  - §2.6「tauri.conf.json 关键字段核对 8/8」→ §7 附录 A 验证方法写"逐项断言（脚本）"；
  - §2.6/§2.9 本地窗口 IPC 冒烟 → "冒烟脚本"；
  - §4.9/§7 附录 A 多实例硬验收 → "自动断言脚本"；
  - §7 附录 A 桥安全 → "安全测试用例"。
  唯一被任务化的断言脚本是 M5 的 `scripts/verify-tauri-release.mjs`（T5.5）。M1–M4 执行到验收时**无脚本可用**，主 KPI 的"可自动断言（命令/脚本）"（§1 头注承诺）名存实亡。
- **涉及小节**：§2.6、§2.9、§4.9、§5.9、§7 附录 A、§1 头注
- **修改建议**：为每处"脚本断言"指定脚本文件路径并挂到现有/新增任务（如 M1 增任务"新建 `scripts/check-tauri-conf.mjs`、`scripts/ipc-smoke.mjs`"；M4 增"多实例硬验收断言脚本、桥安全测试用例"），纳入对应阶段门禁；或降级为"手工执行 + 截图留档"并显式标注，不得只写"脚本"二字。

  2. 发布门禁 verify-tauri-release **P1–P9**（§6.4 T5.5）；

  同一符号"P1"在 §2.2（桥选型决策）与 §6.4-5（构建门禁）含义完全不同，执行者极易混淆。
  另外，SOP §10 对账（L422）声称"前置 P1–P8 均与《代码落地方案报告》**逐字一致**"，但 grep 抽查落地报告全文：前置编号仅见 **P3/P4/P5**（T5.4「P3 前先用测试证书」、T1.4「并入 P4」、T5.5-②「verify-release.mjs P4 思路」、§9-20/§9-24 等，且 P4/P5 同时被用作 verify-release 门禁编号）；**P1/P2/P6/P7/P8 在落地报告中无对应定义**。SOP 正文亦从未使用 P2、P6（L422 的对账是唯一出现处）。"逐字一致"的对账锚点失实（P1/P2/P3/P7/P8 实际出自《可行性分析报告》§7.2，见 SOP L37/L287）。
- **涉及小节**：§2.2、§6.2、§6.4-5、§7 附录 A、§10
- **修改建议**：① 前置编号改为 `Pr1–Pr8`（或 R1–R8）彻底消除与门禁 P 编号冲突；② §10 对账改为"前置项与《可行性分析报告》§7.2 一致"并逐条列出处；③ 对 P2/P6 补定义或从编号集删除，避免悬空编号。

### 【Major-3】决策记录"已落盘"无路径/命名/内容模板，前置条件无法验证
- **描述**：多个决策点要求产出决策记录或"已落盘"，但均未定义文件路径、命名规则、最小内容模板：

### 【Minor-4】READY 兜底轮询无超时/间隔/次数参数

## 二、亮点

1. **步骤整体可执行性强**：T1.x–T5.x 均为文件级/命令级动作且参数具体（Cargo.toml 完整依赖与 features、tauri.conf.json 逐字段值、窗口尺寸 1280×720/480×360、env 键值 `DSH_HOME`/`DSH_HUB_LAUNCHED=1`/`DSH_HUB_SHELL=tauri`、P1–P9 逐项命令），符合 PROCESS_QUALITY §2.3"不写形容词"。
2. **指标量化程度高**：7/7、12/12、8/8、P1–P9、≤3 次重启、1.2s 间隔、30s 冷却、≤5/8/10 工作日全为数字；grep 全文无"尽量/大概/大约"；"插件层零改动"用 `git diff HEAD -- src/client/ … cordis.patch.yml 为空` 硬断言，是 §5.1"可自动断言"的范本。
3. **异常处理针对真实风险且成链**：stdout 伪造闭环（帧前缀 + schema 严格校验 + READY 先验证再导航 + `Child::try_wait` 为准 + `dsh:output` 禁 innerHTML）；EBUSY 按 M1 文件占用 / M4 junction / M5 覆盖安装三场景分别处置；决策点未拍板按默认值推进并标注"待确认"；门禁 FAIL 禁止跳过（铁律 6）。
4. **决策治理完整**：D1–D10 决策点清单带截止阶段/默认值/依据/拍板规则（行为变更类须用户确认、技术权衡类 agent 出具记录），配套 V1–V12 风险清单与"未闭合即阻断里程碑开工"通则。
5. **模板合规**：M1–M5 每阶段含目标/前置/输入/步骤/输出/质量标准/负责人/异常处理/验收方法九要素 + DMAIC 工作表，符合 §8.1；引用三报告为单一事实源而非重抄（§2.3）。
6. **任务号抽查通过**：T1.1–T1.9 / T2.1–T2.6 / T3.1–T3.7 / T4.1–T4.9 / T5.1–T5.7、横切 X1–X4、验收 §9 行 1–28 均与落地报告逐字吻合（M1 引行 22/23/28、M2 引行 1/2/3/6/23/28、M3 引行 4–8/15/17/24、M4 引行 9–18/22/23/26/27/28、M5 引行 19/20/21/24/25/27 全部真实存在）；verify-tauri-release P1–P9 与 T5.5 ①–⑨ 映射一致。

## 三、结论

**可执行性总体达标（附 3 项 Major 修复条件）**：M1–M5 步骤可执行、指标量化、异常与决策闭环、任务号真实、模板九要素齐全，达到 PROCESS_QUALITY §2/§5/§8 的主体要求，可支撑迁移执行。但存在 3 个 Major 阻断项：①验收断言脚本无实现任务（"可自动断言"承诺落空，违背 §5.1）；②P 编号三义冲突且 §10 对账锚点失实（前置 P1–P8 中仅 P3/P4/P5 能在落地报告找到，P1/P2/P6/P7/P8 无定义，违背 §2.3 单一事实源）；③决策记录无路径/模板/验证命令（前置"已落盘"不可验证）。按 §6.1 缺陷分级，Major 须修复或显式豁免：**建议修复上述 3 项 Major（预计半天工作量）后判定"可执行性达标"，否则判定为"有条件达标（M1 动工前须闭合 Major-1/2/3）"**。Minor/Low 项可随 M1 首批 PR 一并修订。
