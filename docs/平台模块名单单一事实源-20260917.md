# 平台模块名单单一事实源（external 基线跟随官方冻结表）

日期：2026-09-17 · 状态：待所有者确认 · 关联：`docs/构建产物可复现性修复-20260917.md`（上一轮）、`docs/关键踩坑记录.md` #110

## 1. 必要性论证

### 1.1 结论：值得做

上一轮收尾时把风险记为「`PLATFORM_MODULES` 与 `SDK_PACKAGES` 两份名单手工维护、存在漂移」。本轮调研**修正了这个判断**，真实情况更具体：

**两份名单职责根本不同，不是同一清单的副本，不该合并。**

| 名单 | 位置 | 语义 | 正确性要求 |
|---|---|---|---|
| `PLATFORM_MODULES`（10 条） | `tsdown.config.ts:14` | 打包期 external 白名单：这些 import 不进包，由宿主冻结表在运行时装 | **必须与官方冻结表逐条一致** |
| `SDK_PACKAGES`（37 条） | `scripts/build-client.mjs:58` | 构建期 junction 清单：把 SDK 包链进 `node_modules` 供 TS/打包器解析 | 宽松超集即可，多链无害 |

### 1.2 真正的风险：`PLATFORM_MODULES` 已与官方冻结表不一致

官方冻结表在 `@deepseek-ai/dsh-web-frontend/dist/assets/index-*.js` 里，实测三个版本（原文提取）：

| dsh 版本 | 冻结表条目 |
|---|---|
| 0.1.2-rc.1（CI 装机版本） | `react`、`react/jsx-runtime`、`react-dom`、`react-dom/client`、`@deepseek-ai/cordis`、`@deepseek-ai/dsh-client-store`、`@deepseek-ai/dsh-client-ui-slots`、`@deepseek-ai/dsh-client-ui-primitives`（**8 条**） |
| 0.1.5-rc.2（本机全局） | 上述 8 条 + `@deepseek-ai/dsh-client-ui-dockkit`（**9 条**） |
| 0.1.6-alpha.1（隔离前缀） | 同 0.1.5（**9 条**） |

与我们名单对账：

- **多标 3 个官方冻结表没有的**：`@deepseek-ai/dsh-client-web-react`、`@deepseek-ai/dsh-client-ui-attachment`、`@deepseek-ai/dsh-client-schema-form`。后果：一旦源码 import 它们，打包器会将其标为 external，产物留下 `require("...")` 由宿主解析；而宿主冻结表不含该键 → 运行时解析失败（插件加载失败/白屏）。**注意**：本计划未实测该失败链路（需构造 import + 实跑宿主），此处依据的是 `dsh-client-modules` README 的解析契约原文：「Resolution checks the platform seed table, memoized records, boot-graph rows, and registered factories in that order; **anything else throws**」（`lib/types/client/manifest.d.ts` 同义表述）。执行时若要确证，按 B3 那样构造一次越界 import 实跑即可。
- **漏标 2 个官方提供的**：`@deepseek-ai/dsh-client-store`、`@deepseek-ai/dsh-client-ui-dockkit`。后果：将来 import 它们会被内联进包，与宿主各持一份实例（React 生态的重复实例风险）。**当前无实际影响**：这两个包均未被 `src/client` import（见 §6 的实际 import 清单），产物内联部分只有 `clsx` 与 `src/client/*`。机制成立的依据是 `tsdown.config.ts:37-40` 的 `alwaysBundle: (id) => !isPlatformModule(id)` —— 不在 external 名单里的一律内联。
- **官方冻结表随版本变化已被证实**（0.1.2→0.1.5 新增 dockkit），说明硬编码名单**必然**随 dsh 升级腐化，且当前没有任何机制能发现它腐化。

### 1.3 受益方与量级

- **仓库维护者**：每次 dsh 升级都要人工比对冻结表（现在无人比对，且已出现 5 条不一致）；修复后由守卫自动报警。
- **用户**：避免「某次功能开发恰好 import 了多标的那 3 个包 → 插件加载即挂」的事故。这 3 个里 `dsh-client-ui-attachment`（附件 UI）、`dsh-client-schema-form`（schema 表单）都是 hub 后续功能容易用到的官方能力。
- 量级：**修复成本约半天，避免的是一类「升级后才炸、且报错指向模糊」的故障**。

### 1.4 现有能力是否覆盖

- `verify-release.mjs` 的 P1–P5 只查身份一致性/装配/漂移/dist-tags，**不查 external 名单**。
- 上一轮新增的守卫只查「产物里有没有绝对路径」，**不查 require 的 specifier 是否是宿主认识的名字**。
- 官方未以可导入形式暴露冻结表（`dsh-client-modules/lib/invariant.js` 仅 1600 字节只含自身包名；`lib/types/client/manifest.d.ts` 无 baseline 常量；`dsh-web-frontend/package.json` 的 `exports` 只有 `./dist/*`，无 `.d.ts`）→ **必须自行从打包产物提取**。

## 2. 需求细化

### 2.1 输入 / 输出

- **输入**：已安装的 dsh 树（`dsh-web-frontend/dist/assets/index-*.js`）+ 仓库内的基线快照文件。
- **输出**：① `tsdown.config.ts` 的 external 名单来自快照而非硬编码；② 构建期守卫：产物 `require` 的 specifier 必须 ⊆ 快照；③ 对账守卫：已安装 dsh 的冻结表与快照不一致时报警并给出更新指令。

### 2.2 边界

- **只读** dsh 安装树（AGENTS.md 铁律 1：不碰 dsh 底层代码）。
- 不改运行时行为、不改发布产物形态、不改 `SDK_PACKAGES` 的宽松语义。
- 不引入新依赖（用 Node 内建即可）。

### 2.3 异常路径（必须显式定义）

| 异常 | 处理 |
|---|---|
| 提取正则匹配不到冻结表（官方改了打包形态） | **硬失败**并打印「提取失败 + 期望形态 + 如何修」；不静默回退（静默回退会掩盖提取逻辑失效） |
| 未安装 dsh（无 SDK 树） | 构建期读**快照**即可（不需要 dsh）；仅对账守卫需要 dsh，缺失时 SKIP 并说明原因 |
| 产物 `require` 了非快照 specifier | 构建失败，列出越界项 + 提示「若确需使用，走官方 `dsh.client.external` 声明」 |
| 已安装 dsh 冻结表 ⊋ 快照（升级新增） | 对账守卫**警告**（不失败）：新增的是宿主能力，保守快照仍安全 |
| 已安装 dsh 冻结表 ⊉ 快照（升级移除） | 对账守卫**失败**：快照里的条目在目标 dsh 上不存在 → 会运行时 throw |

### 2.4 验收标准

| # | 验收项 | 判据 |
|---|---|---|
| B1 | 快照对齐官方 | 快照内容 == 目标基线版本的官方冻结表逐条相等 |
| B2 | 构建产物不变 | 修复前后 `lib/client.js`、`lib/client.js.map` 字节一致（因为多标/漏标的包都没被 import） |
| B3 | 守卫能拦越界 | 临时 import 一个非快照包（如 `@deepseek-ai/dsh-client-ui-dockkit` 之类不入表的）→ 构建非 0 退出并列出越界项 |
| B4 | 对账能报警 | 伪造快照（删一条 / 加一条）→ 对账守卫分别给出「移除」失败与「新增」警告 |
| B5 | CI 全绿 | frontend workflow 9/9 通过，`verify-release` ALL PASS |
| B6 | 跨机可复现 | 本机构建与 CI 构建的 `lib/**` 一致（快照机制保证，不依赖各机安装的 dsh 版本） |

## 3. 技术选型与成本

### 候选 A：运行时提取官方冻结表，直接作为 external 名单 ⭐ 不推荐

从各机已安装 dsh 提取，构建时用提取结果。

- 开发低 / 运行低 / 维护低 / 迁移无。
- **致命缺陷**：CI 装 0.1.2（8 条）、本机 0.1.5（9 条）→ 两机构建出的产物 external 集合不同 → **上一轮刚修好的 P3「lib 零漂移」立刻复活**（本机产物 external 了 dockkit，CI 内联 dockkit）。与「跨机可复现」直接冲突。

### 候选 B：仓库快照为构建源 + 提取用于对账 ⭐ 推荐

冻结表固化为仓库文件（含基线版本号），构建期读快照（确定、跨机一致），另设守卫从已安装 dsh 提取并与快照对账。

- **开发**：中（新模块 ~80 行 + 生成器 + 2 处改动 + 对账守卫）。
- **运行**：零（构建期读一个小 JSON）。
- **维护**：低——dsh 升级时守卫报警 + 生成器一条命令刷新；提取正则只随官方打包形态变化维护（低概率，且失败会硬报错而非静默）。
- **迁移**：无（纯构建期）。
- 满足 B2/B6，不破坏上一轮成果。

### 候选 C：保持硬编码 + 仅加对账守卫

- 开发低 / 运行零 / 维护中（仍需人工改名单，守卫只告诉你「该改了」）/ 迁移无。
- 治标：漂移可见但不自动消除，且每次升级仍需手工誊抄两份清单。

**推荐 B**。理由：唯一同时满足「跨机可复现」「不随 dsh 升级腐化」「漂移可见」三项的方案；C 是它的退化版，A 与上一轮成果冲突。

### 快照基线取值（保守交集原则）

external 集合必须在**所有支持的 dsh 版本**上都能解析，否则低版本上运行时 throw。故快照取**最低支持版本基线**：`package.json` peerDeps 声明的 `^0.1.2-rc.1` → 即 0.1.2-rc.1 的 **8 条**（它同时是 0.1.5 冻结表的子集，向上兼容安全）。

最终名单（8 条，= 官方 0.1.2 冻结表）：

```
react, react/jsx-runtime, react-dom, react-dom/client,
@deepseek-ai/cordis, @deepseek-ai/dsh-client-store,
@deepseek-ai/dsh-client-ui-slots, @deepseek-ai/dsh-client-ui-primitives
```

对比现状的变化：**移除** 3 条（`dsh-client-web-react` / `dsh-client-ui-attachment` / `dsh-client-schema-form`，均未被 import）、**新增** 1 条（`dsh-client-store`，未被 import）→ 因这些包都未参与打包，**产物字节应零变化**（B2 可验证）。

## 4. 架构与解耦约束

```
scripts/dsh-sdk-scope.mjs          ← 共享定位（新，从 build-client.mjs 抽出 dshSdkScope）
        ↑                    ↑
scripts/dsh-platform-modules.mjs   ← 冻结表提取 + 快照读取（新）
        ↑                    ↑
tsdown.config.ts（构建期消费者）   build-client.mjs（守卫消费者）
        ↑                    ↑
scripts/verify-platform-modules.mjs ← 对账守卫（新，verify-* 命名族，CI 触发路径已通配覆盖）
```

- **依赖方向**：配置/脚本 → 共享工具模块，单向；共享模块**不得** import 消费者（避免 `build-client.mjs` 顶层 `main()` 被执行）。
- **分层**：全部属构建期工具层（`scripts/`），不进 `src/`，不污染运行时依赖图。
- **事实源单一**：快照文件是构建期唯一事实源；已安装 dsh 是**对账参考**，不参与构建决策（这是与候选 A 的关键差别）。
- **扩展点预埋**：快照含 `baseline`（版本号）、`modules`（名单）、`source`（提取自哪个文件）三字段，便于将来加「多版本区间」而不用改结构。
- **`SDK_PACKAGES` 保持不动**（职责不同，宽松超集）；但可后续单独评估「与 devDeps 的 dsh 包列表同步」，属独立议题。

## 5. 模块拆解与执行步骤

每步均可单步验证。

**S1｜抽出共享定位模块**
- 目标：`scripts/dsh-sdk-scope.mjs` 导出 `resolveDshSdkScope()`（从 `build-client.mjs:23-55` 的 `dshSdkScope()` 原样搬移）。
- 输入：现有 `build-client.mjs`。
- 预期输出：新模块；`build-client.mjs` 改为 import 它，行为不变。
- 验证：`node scripts/build-client.mjs` 输出仍为 `linked N SDK packages from ...`；`git diff lib/` 为空。

**S2｜写冻结表提取器 + 快照生成**
- 目标：`scripts/dsh-platform-modules.mjs` 导出 `extractOfficialPlatformModules(sdkScope)`（读 `dsh-web-frontend/dist/assets/index-*.js`，正则提 `{react:..,"react/jsx-runtime":..}` 的键集合，处理「合法标识符键不带引号」两种形态），附 CLI：`node scripts/dsh-platform-modules.mjs --write-snapshot`。
- 输入：dsh 安装树。
- 预期输出：`scripts/dsh-platform-modules.json`（`baseline` / `modules` / `source`）。
- 验证：CLI 输出 8 条且与 §3 清单逐条相等；对 0.1.5 树跑一次应得 9 条（证明提取器感知版本差异，用 `DSH_CMD` 指向隔离前缀即可测）。

**S3｜tsdown.config.ts 改为读快照**
- 目标：`PLATFORM_MODULES` 改为从快照导入；保留 `isPlatformModule` 与 `deps.neverBundle/alwaysBundle` 结构不变。
- 输入：快照文件。
- 预期输出：配置同步读取（`readFileSync` + `JSON.parse`）。
- 实现注意：配置是 TS 文件、由 tsdown 加载，路径**必须**用 `fileURLToPath(new URL('../scripts/dsh-platform-modules.json', import.meta.url))` 而非 `process.cwd()` 拼接——本机路径含中文时 `import.meta.url` 直接使用会被 URL 编码（历史踩坑），且 cwd 依赖会让「从子目录调用」出错。
- 验证：`npm run build:client` 通过；产物 `require` 集合仍为 5 条（见 §6 证据）；`git diff --stat lib/` 为零。

**S4｜构建期守卫扩展**
- 目标：`build-client.mjs` 的 `assertPortableArtifacts()` 增加第二段——产物 `require("X")` 的 specifier 必须 ⊆ 快照 modules；越界则打印越界项 + 「若确需使用，走官方 `dsh.client.external` 声明」并 `exit 1`。
- 输入：产物 + 快照。
- 预期输出：守卫函数。
- 验证（B3）：临时在 `src/client/index.ts` 加一行 import 一个非快照包 → 构建失败并列出该项；撤销后恢复通过。

**S5｜对账守卫**
- 目标：`scripts/verify-platform-modules.mjs`：提取已安装 dsh 冻结表 ↔ 快照对账。快照有而 dsh 无 → FAIL；dsh 有而快照无 → WARN 并提示 `--write-snapshot` 刷新；dsh 缺失 → SKIP。
- 输入：快照 + dsh 树。
- 预期输出：可独立运行的守卫脚本（退出码语义同 `verify-*.mjs` 家族）。
- 验证（B4）：手工改快照加一条假项 → FAIL；删一条真项 → WARN；还原 → PASS。

**S6｜CI 触发路径补一条**
- 目标：`.github/workflows/frontend.yml` 的 `push.paths` 与 `pull_request.paths` 增加 `scripts/dsh-platform-modules.json`（新模块与守卫已被既有 `scripts/verify-*.mjs`、`scripts/build-client.mjs` 通配覆盖，仅快照文件漏网）。
- 验证：`js-yaml` 解析通过；paths 各含该条目。

**S7｜门禁串联**
- 目标：`verify-release.mjs` 增加 P6 调用对账守卫（或在 README/发布流程中登记为独立步骤）。
- 验证：本地 `node scripts/verify-release.mjs` 全 PASS。

**S8｜文档同步**
- 目标：`docs/关键踩坑记录.md` 追加 #111（官方冻结表位置/随版本变化/多标漏标事故面）；`README.md` 构建章节补一句 external 名单来源；本文件状态改为「已执行」。
- 验证：编号唯一；行尾与既有文档一致（LF）。

**S9｜提交推送验证**
