### 壳内 HTML5 拖拽全灭修复（用户对照反馈定案：浏览器可拖、壳内不能拖）
- 现象：官方左侧栏工作区行拖拽排序在壳内完全失效（"被固定住"）；同一 dsh 页面在普通浏览器正常
- **主根因（壳层）**：Tauri 2.x `dragDropEnabled` 默认 true → wry `DragDropController` 对每个 WebView2 子 HWND `RevokeDragDrop` + `RegisterDragDrop`（只认文件 CF_HDROP + `SetAllowExternalDrop(false)`）——页内 HTML5 DnD 事件链在 OS 层被整体截走。Tauri 官方文档自认"Windows 上用 HTML5 DnD 必须禁用"；Rust 手工建窗不受 tauri.conf.json 配置影响（tauri#13761），同型 issue #2014/#15138
- 修复三层（不改官方 dsh 源码）：
  1. `window.rs` builder 加 **`.disable_drag_drop_handler()`**——恢复 WebView2 默认 IDropTarget，页内 DnD 行为回归 Chrome；壳不消费任何 tauri drag-drop 事件，零功能损失
  2. `shell-init.js` **Files-only 拖放兜底**（document capture 阶段 dragover/drop preventDefault）——撤覆盖后拖文件到输入区 = 官方附件上传（新行为，见注意事项）；无 drop 处理器的空窗期兜住，杜绝拖入文件被当 file:// 导航
  3. `src/client/workspace-drag-guard.ts` **精简**：撤掉上一轮误判根因时加的 dragover 拦截（会让"拖到最前"失去官方顶部插入线），保留 watchdog 合成 dragend 自愈（兜底官方 flip-OFF 重建吞 dragend 的次生缺陷）+ 拖拽时收缩置顶区
- 踩坑 #94 改判重写：主根因=壳层 IDropTarget 覆盖；"官方无 key 重建 → dragend 丢失"降级为浏览器侧次生缺陷（壳内 dragover 都不派发，轮不到触发）
- **方法学教训**：合成 DragEvent 不经过 OS IDropTarget/wry 拦截层——上一轮用 CDP 合成事件验证得到假阳性；真实鼠标拖拽壳内 vs 浏览器对照才是判据
