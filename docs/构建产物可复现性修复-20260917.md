# 构建产物可复现性修复（lib 产物路径与行尾归一化）

日期：2026-09-17 · 状态：待执行（待所有者确认） · 关联：`.gitattributes` eol=lf 修复（commit e591d87）

## 1. 背景分析

### 1.1 遗留问题是什么

上一轮修掉 CI 门禁的两个失败（pwsh 误用 bash 语法、autocrlf 导致的幻影漂移）后，剩余一条未处理项：**构建产物不可跨环境复现**——同一份源码在不同机器/目录下构建，会产出字节不同的 `lib/client.js` 与 `lib/client.js.map`。

### 1.2 两个独立机制（均有实测证据）

**机制 A：依赖经符号链接/junction 指向仓库外时，打包器把模块路径写成绝对路径。**

- 实测：克隆到 `C:\...\leakfix` 后把 `node_modules` 做成指向 `G:\DSH\MarecGents-hub\node_modules` 的 junction，构建产出：
  - `lib/client.js:15` → `//#region G:/DSH/MarecGents-hub/node_modules/clsx/dist/clsx.mjs`（已提交版本是 `//#region node_modules/clsx/dist/clsx.mjs`）
  - `lib/client.js.map` 的 `sources[0]` → `G:/DSH/MarecGents-hub/node_modules/clsx/dist/clsx.mjs`（已提交版本是 `../node_modules/clsx/dist/clsx.mjs`）
  - 共 1 条 region + 2 条 sources 命中，`git status` 报 2 个文件 M。
- 触发条件：被打包的依赖其解析路径在仓库根之外。本仓库当前不触发（`node_modules/clsx`、`node_modules/@xterm/xterm` 都是仓内实体目录），但**潜在触发面明确**：
  - `scripts/build-client.mjs:73-92` 会把 15 个 `@deepseek-ai/dsh-*` 包 junction 进 `node_modules/@deepseek-ai/`，目标是全局 dsh CLI 树（仓外）。这批包当前全部在 `tsdown.config.ts` 的 `PLATFORM_MODULES`（external）里所以不进包；**一旦某天源码 import 了不在 external 名单里的 SDK 包，它会被打进产物并携带仓外绝对路径**——external 名单与 SDK 名单是两份手工维护的列表，存在漂移风险。
  - 开发机把 `node_modules` 共享/软链（省空间）时直接触发。

**机制 B：sourcemap 的 `sourcesContent` 原文捕获构建机的工作区行尾。**

- 实测：已提交的 `lib/client.js.map` 里 30 条 `sourcesContent` 有 **28 条含 CRLF**（作者在 Windows CRLF 工作区构建）；而 LF 工作区（`core.autocrlf=false` 克隆）构建出的地图 **0 条含 CRLF**。
- 这是当前 CI 仍绿的原因：Git for Windows 默认 `core.autocrlf=true`，CI 与作者本机的工作区都是 CRLF（`src/**` 未钉行尾），两边 `sourcesContent` 都是 CRLF，于是字节一致、P3 报 clean。**但这种一致是巧合性一致**：任何 LF 检出环境（Linux/macOS/CI 设了 autocrlf=false）构建出的地图都会与仓库里的产物不同，P3 立刻红。

### 1.3 为什么值得修（不是洁癖）

1. **CI 门禁的语义完整性**：P3「lib 零漂移」的本意是「仓库产物 == 新鲜构建产物」。现在它在 LF 环境下会误报（真失败），在 junction 环境下会漏报（产物已变但门禁只对比提交态）。
2. **发布产物可审计**：`verify-release` P4 会把 `npm pack` 出的 tgz 装进干净环境冒烟；产物里嵌构建机绝对路径属于信息泄漏面（虽非密钥），也让「同一版本号两次构建结果不同」无法复现。
3. **成本**：修复只需在一个构建脚本里加约 40 行归一化 + 重生成一份地图，无需改动运行时代码。

### 1.4 影响范围（实测界定）

| 产物 | 是否受机制 A | 是否受机制 B | 结论 |
|---|---|---|---|
| `lib/client.js` | 是（region 注释） | 否（输出本身是 LF） | 归一化后与已提交版本**逐字节相同**（Δ0），无需重提交 |
| `lib/client.js.map` | 是（sources） | 是（sourcesContent） | 归一化后与已提交版本不同（Δ−21176 字节，全是 CR），**需重生成并提交** |
| `lib/**.d.ts` / `**.js`（tsc 产物） | 否 | 否 | 仅行尾敏感，已由 `.gitattributes` `lib/** eol=lf` 覆盖 |
| `plugins/*/lib` | — | — | 未被 git 跟踪（0 个文件），不在本轮范围 |

### 1.5 已验证的关键事实（供实现直接引用）

- 归一化规则的正确性已被实测证明：把「LF 克隆 + junction」的构建产物按下文规则归一化后，与「CRLF 工作区 + 仓内实体依赖」的构建产物**完全一致**（client.js 1041749 字符、map 1592778 字符，两侧相等）。
- 地图 JSON 的 `parse → stringify` 往返**字节无损**（实测 1625660 字节进出一致，无 BOM、无尾随换行），因此可安全用结构改写而非文本替换。文本替换反而不可用：地图里路径是 JSON 转义形态，实测 59 个候选片段替换命中 0 个。
- 归一化目标形态（取自已提交产物，即「干净环境」的自然输出）：
  - region：`node_modules/clsx/dist/clsx.mjs`、`src/client/style.ts`（仓库相对，无前导 `./`；虚拟模块为 `\0rolldown/runtime.js`，**必须豁免**——它不以 `/` 开头但含 `\0` 前缀，见 §3 判定函数）
  - map.sources：`../node_modules/clsx/dist/clsx.mjs`、`../src/client/skins.ts`（以 `lib/` 为基准的相对路径）
  - map.sourcesContent：LF 统一（去 CR）

## 2. 方案设计

单一改动点：**在产物生成处（`scripts/build-client.mjs`）追加一个归一化步骤**，紧随 tsdown 之后、进程退出之前执行。理由：这是两个产物的唯一生产者，归一化放这里对「手动构建 / `npm run build:installer` / CI」三条路径同时生效，无遗漏面。

规则（按序）：

1. `lib/client.js`：文本级替换 `//#region <path>` 中的绝对路径。
   - 路径在仓库根内 → 切成仓库相对路径；
   - 在仓库根外（junction）→ 取**最后一个** `/node_modules/` 之后的部分并前缀 `node_modules/`；
   - `\0` 开头的虚拟模块不视为绝对路径，跳过。
2. `lib/client.js.map`：`JSON.parse` → **两个字段**改写 → `JSON.stringify`（不带尾随换行，与现状一致）。
   - `sources`：同规则映射，但前缀 `../`（相对 `lib/`）；
   - `sourcesContent`：CRLF → LF。
3. 归一化后自检：再扫一遍 `lib/client.js` 的 region 与 `lib/client.js.map` 的 `sources`，**若仍存在绝对路径 → 打印命中条目并 `exit 1`**（让机制 A 的潜在触发面在构建期大声暴露，而不是静默产出脏产物）。

刻意**不做**的事（避免过度设计）：

- 不改 `tsdown.config.ts` 的 external 名单逻辑（那是另一个议题，且改动风险高于收益）；
- 不在 `verify-release.mjs` 里加静态断言：构建期自检 + P3 漂移检查已构成双保险，再加一层只会增加门禁的维护面；
- 不改 `src/**` 的行尾（改了会动到开发者的工作区体验；归一化在产物侧解决同一问题）。

配套改动（必要的两处，否则修复无法被 CI 验证）：

- `.github/workflows/frontend.yml` 的 `paths` 增加 `scripts/build-client.mjs` 与 `lib/**`：当前触发清单只含 `scripts/verify-*.mjs`，**本次改动（build-client.mjs + lib/client.js.map）落不到任何触发路径上，CI 根本不会跑**。
- `docs/关键踩坑记录.md` 追加一条（编号顺延 #110）：记录机制 A/B 与判定指纹。

## 3. 实施步骤

1. **改 `scripts/build-client.mjs`**：顶部补 `readFileSync, writeFileSync`（`node:fs`）与 `posix`（`node:path`）导入；新增 `normalizeArtifacts()` 与 `isAbsoluteModulePath()`；在 `main()` 里 tsdown 成功返回后调用。

   ```js
   /** 绝对路径判定：盘符（C:/ 或 C:\）、UNC（\\）、POSIX 根（/）；\0 虚拟模块豁免。 */
   function isAbsoluteModulePath(p) {
     if (p.startsWith('\\0')) return false
     return /^[A-Za-z]:[\\/]/.test(p) || /^\\\\/.test(p) || p.startsWith('/')
   }

   /** 绝对路径 → 归一化形态；在仓内用仓库相对路径，仓外退回 node_modules/ 相对。 */
   function normalizeModulePath(absPath, basePrefix = '') {
     const fwd = absPath.replace(/\\/g, '/')
     const rootFwd = PACKAGE_ROOT.replace(/\\/g, '/')
     if (fwd.startsWith(rootFwd + '/')) return basePrefix + fwd.slice(rootFwd.length + 1)
     const cut = fwd.lastIndexOf('/node_modules/')
     return basePrefix + (cut >= 0 ? fwd.slice(cut + 1) : fwd)
   }
   ```

   - `client.js`：`content.replace(/\/\/#region ([^\r\n]*)/g, ...)`，逐条 `isAbsoluteModulePath` 判定后替换；
   - 地图：`sources` 映射用 `basePrefix = '../'`，`sourcesContent` 统一 `replace(/\r\n/g, '\n')`，再 `writeFileSync(dest, JSON.stringify(parsed))`；
   - 自检不通过时：`console.error` 列出命中路径 + 提示「依赖可能经符号链接指向仓库外」，`process.exit(1)`。

2. **本地重生成产物并核对差异**（预期：`lib/client.js` 无变化、`lib/client.js.map` 仅去掉 CR）：

3. **四环境一致性验证**（不装依赖，用 junction 造最坏条件；CI 负责真·仓内依赖环境）：

